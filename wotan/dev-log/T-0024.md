# T-0024: Write the formalization process history

**Status**: DONE | **Size**: L
**Phase**: -

## Context

Produce a second, deliberately different report: an evidence-based account of how
the formal specification and proofs came into being. It may discuss project-control
and Wotan because they are part of its subject, but it must synthesize the record into
an intelligible methodological narrative rather than reproduce logs or commit lists.

## Acceptance Criteria

- [x] Write a polished English LaTeX report with a clear narrative thesis, abstract,
  evidence basis, references, and conclusion.
- [x] Reconstruct how informal paper claims were scoped, disambiguated, decomposed,
  strengthened, weakened, or isolated behind explicit interfaces.
- [x] Explain pivotal mathematical and Lean engineering decisions, failed approaches,
  discovered constraints, corrective loops, and the evidence that resolved them.
- [x] Use Wotan logs, project-control records, Git history, diffs, build evidence, and
  source-audit findings critically; distinguish contemporaneous evidence from later
  interpretation.
- [x] Show the evolution of the proof dependency structure and verification standard
  without becoming a raw chronological diary.
- [x] Extract general lessons for formalizing interdisciplinary mathematical papers,
  including assumptions, approximation boundaries, library reuse, and proof trust.
- [x] Include failures and residual uncertainty honestly, without turning the report
  into a celebration or a procedural manual.
- [x] Compile the LaTeX source to a stable PDF under `output/pdf/`, render every page,
  and correct all content, typography, pagination, table, figure, citation, and
  accessibility defects found in visual and textual QA.

## Verification Plan

### Hard Endpoints

- [x] Every material historical claim is supported by a cited repository artifact,
  commit, build record, or source-audit finding.
- [x] LaTeX compilation completes without unresolved references or citations.
- [x] PDF metadata and extracted text contain all intended sections and no
  placeholders.
- [x] Every rendered page passes visual inspection at readable resolution.

### Manual Checks

- [x] The report explains causality and tradeoffs rather than merely ordering events.
- [x] It remains readable to researchers who did not participate in the project.
- [x] It does not duplicate the scientific report's role or hide important setbacks.

### Risks

- Retrospective narrative can impose false inevitability. Preserve alternative paths,
  uncertainty, and dated evidence where they affected decisions.
- Repository logs vary in granularity. Corroborate them with commits and code rather
  than treating any single record as complete.

## Approach

Build an evidence timeline, then reorganize it around a few explanatory arcs: turning
paper prose into theorem contracts, developing the geometric and finite-dimensional
core, confronting analytic and probabilistic approximations, expanding source and
axiom audits, and learning where formal proof ends. Use chronology inside those arcs
only where it explains why the resulting architecture took its form.

## Implementation Notes

T-0023 fixed the final audited mathematical scope and published the separate
non-chronological scientific account. The process report can now use that stable
result as its destination while concentrating on evidence, decisions, failed paths,
and methodological lessons.

Work began by freezing T-0023 in commit `5a83b13` and opening a structured evidence
review. Historical propositions will be drafted only after they can be tied to dated
Wotan entries, project-control decisions, commits or diffs, build results, and the
source audit. The report will organize those propositions into causal arcs rather
than reproduce the repository chronology.

The evidence review is preserved in `reports/process-history-evidence.md`. It assigns
provenance classes and stable evidence identifiers to the feasibility study, every
proof arc, the steering gates, Git states, the source audit, and report QA. It also
records negative evidence and the limits of commit timestamps and self-authored logs.

The owner identified the complete Codex JSONL session trace under `~/.codex/`. A
privacy-conscious audit of a SHA-256-bounded prefix is preserved in
`reports/session-trace-audit.md`. Contrary to the initial evidence-matrix caveat, the
trace contains full successful patch payloads and compiler feedback for the discarded
scratch developments. It records 174 change events over 33 scratch/probe/audit files,
so the process report can reconstruct failed and superseded proof routes rather than
infer them only from clean commits.

The final report, `reports/formalization-process-history.tex`, is organized around
theorem-contract refinement, dependency-led architecture, three different classes of
failure, analytic and probabilistic witness construction, steering, and the growth of
the verification standard. Chronology is confined to an appendix; a separate
26-entry evidence ledger makes the provenance of material claims explicit.

## Obstacles

The first evidence matrix was too pessimistic about discarded work because it had not
yet inspected the complete Codex session trace. The owner's pointer to `~/.codex/`
changed the historical conclusion: tool-mediated scratch edits and failed proof
routes are unusually well preserved. The report now states both that positive result
and its privacy boundary.

The first LaTeX build exposed an unescaped `#` and an invalid stretch column in a
`longtable`. Later visual QA found a diagram isolated on a float page, an orphaned
section heading, and a final evidence item spilling onto an almost empty page. The
source was corrected and the complete 25-page artifact was rerendered and reinspected.

## Outcome

The process history gives a causal, evidence-qualified account of how the paper's
informal claims became theorem contracts and checked endpoints. It distinguishes
local elaboration failures from architectural changes and mathematical obstructions,
shows how explicit interfaces prevented unsupported claims, and records both the
speed and the limitations of autonomous proof production. The owner's session-log
correction materially strengthened the report by replacing an unsupported absence
claim with a checksum-bounded reconstruction of discarded scratch work. Project-
control checkpoint PCR-025 closes the approved formalization, source-audit, and
two-report program while preserving genuinely open empirical and specification work
as explicit nonclaims.
